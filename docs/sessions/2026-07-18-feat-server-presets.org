* Decisions Made
- *Extend =MarkerResolver= with =LanguageFor= rather than a new resolver type.*
  TypeScript/JSX need a per-extension languageId (tsx→typescriptreact,
  jsx→javascriptreact) that a single fixed =Language= field can't express. A
  parallel type would duplicate the FindUp/marker-walk logic; a nil-safe
  optional field keeps every existing =MarkerResolver= user (PythonResolver,
  any external caller) byte-for-byte unchanged. Verified via WebFetch of the
  LSP 3.17 spec's language-identifier table: "typescript"/"typescriptreact"/
  "javascript"/"javascriptreact"/"rust" are exactly the values documented
  there — not a guess.
- *Shared tsconfig.json > jsconfig.json > package.json marker precedence for
  BOTH TypeScriptResolver and JavaScriptResolver* (=nodeMarkers=): a
  JavaScript-only project may still carry a tsconfig.json for `allowJs`
  editor tooling, so the more-specific config should win even when resolving
  a .js file.
- *No exttool dependency, ever, in lspbridge.* exttool
  (github.com/davidwalter0/exttool) declares/resolves/installs
  typescript-language-server and rust-analyzer with real version pins (see
  its =pkg/manifest.DefaultManifest=), but it has its own go.sum. Importing
  =github.com/davidwalter0/exttool= (the root package with =Require=) would
  pull that in and break lspbridge's zero-external-dependency invariant. The
  compromise: =missingBinaryError= only *names* the remediation command
  (`exttool install --tool NAME --confirm`) as a string — no import, no
  shell-out, no version number duplicated (so it can never drift out of sync
  with exttool's manifest pins the way a hardcoded copy would).
- *rust-analyzer Spec passes no arguments.* Confirmed via
  `rust-analyzer --help`: unlike pyright/typescript-language-server, running
  the bare binary with no subcommand IS the LSP-over-stdio mode; its
  subcommands are parser/debug utilities, not alternate transports.
- *tsserver's broker proof is the one that must go "through the broker";
  rust-analyzer's does not (per the task's own framing).* Implemented
  accordingly: =pkg/broker/broker_tsserver_live_test.go= dials a REAL unix
  socket with an ALL-DEFAULT =broker.Config{}= to prove
  =projectcontext.DefaultChain= + =broker.DefaultSpecFor= resolve a Node
  project end-to-end; rust-analyzer's proof stays at the simpler
  =pkg/server= layer (direct Launch+Initialize+DocumentSymbol), which also
  reduces flake surface for a server known to be slow to index. Empirically,
  on this host, rust-analyzer answered documentSymbol for a tiny std-only
  crate in 0.4s with no indexing wait — but the honest-skip-not-fail
  fallback (a generous 90s deadline, then =t.Skip=, not =t.Fatal=) is
  implemented anyway per the task's explicit caution, since a cold/slow host
  could differ.
- *No pyright.go changes.* The task asked for the exttool-hint error text on
  the two NEW specs only; retrofitting =PyrightSpec='s error text was out of
  scope and left untouched to keep the diff minimal.

* Glossary
- Node ProjectContext :: the (tsconfig.json | jsconfig.json | package.json)
  root/config discovery seam for the JS/TS family, the Node-specific
  instance of the generic projectcontext.Resolver seam
- LanguageFor :: MarkerResolver's optional per-extension languageId hook
  (nil = fixed Language, as before)
- languageId :: the LSP TextDocumentItem field; "typescriptreact"/
  "javascriptreact" are the JSX-flavored variants per the LSP spec
- exttool :: github.com/davidwalter0/exttool, this ecosystem's declared
  non-Go tool installer/pin-tracker; lspbridge names its remediation command
  but never imports it
