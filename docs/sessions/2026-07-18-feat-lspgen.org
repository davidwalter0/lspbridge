* Session Topic
Implement mgmt 8a6c4d87: generate lspbridge's pkg/lsp protocol types from the
pinned LSP 3.18 metaModel.json via a new stdlib-only cmd/lspgen generator,
because the hand-written todo's own trigger fired — the method surface grew
past the "~5 more methods" threshold (lifecycle + documentSymbol/references/
definition/hover/rename/foldingRange/workspace-symbol + publishDiagnostics).
Must be a strict drop-in: zero behavior change, every existing test in both
the root module and the org-lsp nested module passes unchanged.

* Decisions Made
- *Types only, no method bindings.* The original todo's context mentions
  "types+method bindings"; this session's actual instructions scope it to
  types. Client's request methods (DocumentSymbol, References, Definition,
  Hover, Rename, FoldingRange, WorkspaceSymbol) and their null/polymorphic
  decoding helpers stay 100% hand-written — that's behavior/judgment
  (discrimination, normalization), never a mechanical data shape.
- *A configured allowlist, not the whole 387-structure metaModel.* Per the
  todo's own instruction. cmd/lspgen/config.go is the single source of
  truth for which structures/enums generate, in what field subset/order,
  and with what per-field overrides — and carries the full exclusion
  rationale as its header doc comment so the "why" travels with the code,
  not just this session trace.
- *Extends always flattens in fully; mixins never auto-include.* The
  metaModel distinguishes real inheritance (extends — SymbolInformation
  IS-A BaseSymbolInformation) from additive traits mixed into dozens of
  unrelated Params types (WorkDoneProgressParams/PartialResultParams, for
  progress-token support lspbridge's client never sends). One blanket rule
  — flatten extends, drop mixins — reproduced the pre-existing hand-written
  field set for EVERY *Params type checked, with no per-type exclude list
  needed.
- *Per-field overrides are declared, not improvised, and always carry a
  reason string rendered into the generated file's doc comment.* Six
  fields needed one: Diagnostic.code (int|string -> any, matches the
  pre-existing hand-written type), Diagnostic.message (3.18 widened this to
  string|MarkupContent behind a capability lspbridge doesn't advertise ->
  kept string), MarkupContent.kind and TextDocumentItem.languageId (both
  reference open string enums in spec, but every real call site
  — pyright.go, broker.go, existing tests — passes/compares a plain string
  local, so the enum reference would be a breaking type change -> kept
  string), FoldingRange.start/endCharacter (spec optional-uinteger, but 0 is
  a meaningful value distinct from "unset" -> kept the pre-existing *int
  pointer override), InitializeResult.capabilities (kept raw json.RawMessage
  rather than modeling ServerCapabilities, by far the largest structure in
  the whole metaModel).
- *Five types stay fully hand-written*, each because it carries genuine
  behavior (a custom UnmarshalJSON normalizing a polymorphic or
  multi-wire-form field) or is an invented shape with no metaModel
  structure of its own: WorkspaceEdit (+ TextDocumentEdit /
  OptionalVersionedTextDocumentIdentifier), Hover, TextDocumentContentChangeEvent,
  DocumentSymbolResult, InitializeParams. Full rationale for each lives in
  cmd/lspgen/config.go's header comment (DRY: not re-explained per-file).
- *Diagnostic gains RelatedInformation (+ the new DiagnosticRelatedInformation
  type), and nothing else new*, deliberately matching the todo's explicit
  "Diagnostic(+related)" instruction rather than adding Tags/CodeDescription/
  Data too (all equally mechanical, all left as a documented next step) —
  scope discipline over "generate everything spec allows."
- *LocationLink is generated as new, unused surface* (the todo's own
  allowlist names it explicitly as near-term). Client.Definition doesn't
  advertise linkSupport so no server sends it today; it costs nothing to
  have the type ready.
- *Determinism is a hard requirement, verified two ways*: an in-process
  test (Generate() called twice, byte-equal) is necessary but not
  sufficient on its own to prove `go generate` itself is stable across
  process boundaries (e.g. map-iteration nondeterminism wouldn't
  necessarily show up the same way) — so the session additionally ran two
  independent `go generate` process invocations and diffed the output
  byte-for-byte.
- *No integration worktree; direct --ff-only merge onto primary's main*,
  matching the immediately preceding org-lsp session's own precedent for
  this same repo (no remote configured; a separate integration/<date>
  worktree adds no value for a single linear feature landing solo).

* Glossary
- metaModel.json :: the LSP project's own machine-readable protocol
  description (structures/enumerations/typeAliases/requests/notifications);
  source of truth this generator reads instead of hand-transcribing types
- allowlist :: cmd/lspgen/config.go's structConfigs/enumConfigs — the
  deliberately small subset of the metaModel's 387 structures this
  generator actually emits
- fieldOverride :: a config.go entry that replaces the mechanically-resolved
  Go type for one "Structure.property" with an explicit type + a reason
  string, used only where the default rule would break an existing call
  site or overreach into unmodeled spec surface
- extends vs mixins :: the metaModel's own distinction between real
  inheritance (flattened in fully by this generator) and additive
  progress-token traits (never auto-included)
- drop-in :: this migration's hard constraint — every pre-existing test,
  in both lspbridge modules, must pass completely unchanged
